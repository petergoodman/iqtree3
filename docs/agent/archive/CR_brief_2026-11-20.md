## Findings

### File layout (comment 1)

NQC's new code is five files:

| File | Lines | Role |
|---|---|---|
| `model/fixedeqchart.h`, `.cpp` | 134, 446 | the pure chart: Eigen only, no IQ-TREE headers, no static mutable state (section 2.1) |
| `model/modelnonrevfixedeq.h`, `.cpp` | 161, 898 | the model class (section 2.2) |
| `model/linkedmodelhooks.h` | 49 | the abstract interface `PartitionModel` calls for linked fits (decision 005) |

In IQ-TREE's layout each model is one `.h` and `.cpp` pair (`modelmarkov`, `modelprotein`), so "one
file" in practice means one pair. A merged `.cpp` of about 1350 lines would be within IQ-TREE's
range (`modelmixture.cpp` is several thousand).

Any layout keeps the edits to shared files: `modelmixture.cpp` (dispatch and mixture refusal),
`modelprotein.{h,cpp}` (protected constructor), `partitionmodel.{h,cpp}` (derivative delegation and
the two linked calls), `main/phyloanalysis.cpp` (report call and citation), `utils/tools.{h,cpp}`
(`--nqc-domain` and the help lines), and `model/CMakeLists.txt`. That is eight source files and
the build list (the session's chat said "seven"; this count is the correct one). The maintainers
should hear that a one-file NQC still needs them.

**Hooks.** `linkedmodelhooks.h` says it is separate because NQC's header is included by
`modelmixture.cpp` and `partitionmodel.h` pulls in the super tree, so placing the interface in
either header would create an include cycle. That reasoning concerns headers. Of the project's
headers, NQC's includes only `fixedeqchart.h`, `linkedmodelhooks.h` and `modelprotein.h` (besides
Eigen, `<cstdint>` and `<vector>`), so `partitionmodel.cpp`, a source
file, can include it without a cycle (from the include lines; not compiled). Two ways to fold the
file away:

- move the interface into NQC's header unchanged;
- drop the interface and have `PartitionModel` cast to `ModelNonrevFixedEq` directly. Nothing else
  implements the interface, so it is an abstraction with one user. This rewrites decision 005's
  rule text.

Either way the same models take the same paths, so behaviour is unchanged. Agent's recommendation:
the direct cast.

**Chart.** Moving the code is mechanical: it is compiled in the same `model` target with the same
flags. The cost is the C++ unit tests. Decision 012's standalone project compiles
`fixedeqchart.cpp` with Eigen alone; a file that includes IQ-TREE headers (`modelprotein.h` and,
through it, generated configuration) cannot be compiled that way. Options:

- **(a)** Keep the chart as a second pair and give the maintainers the reason: pure functions,
  tested alone, safe in `PartitionModel::targetFunk`'s OpenMP loop. Four files instead of five.
- **(b)** Merge, and move the unit tests into the main build as an opt-in target linking the `model`
  library and its dependencies (the alternative decision 012 did not choose).
- **(c)** Merge, with the chart fenced by a preprocessor guard that the unit test defines, so it
  compiles only that part. It works, but maintainers may find it worse than two files.

Agent's recommendation: (a), with (b) as the fallback if one pair is required. A merge under (b) or
(c) also changes `fixedeq.yaml`, `CODE_PLAN.md` sections 1.1, 2.1, 3.2 and 5, and
`model/CLAUDE.md`. `ARCHITECTURE.md` describes upstream code and is unaffected.

### Reuse (comment 2)

The review is read-only, so it carries no risk to SIM-2, and it comes before any refactor because it
decides what the refactor should contain. Proposed output, two tables:

- **Code.** Each NQC override (`targetFunk`, `derivativeFunk`, `setBounds`, `optimizeParameters`,
  `decomposeRateMatrixNonrev`, the state-frequency and rate-matrix setters, the checkpoint trio,
  `setVariables`, `getVariables`) and each chart function, against its nearest `ModelMarkov`,
  `ModelProtein` or NONREV counterpart. Each row is classed as calls the base unchanged, wraps it,
  reimplements it, or has no counterpart, with the reason and whether reuse is possible now.
  `CODE_PLAN.md` 1.2's "Why the file must change" column already covers the shared edits.
- **User-facing.** Each step of the nQMaker workflow (single fit, `-S` with a directory or partition
  file under `--model-joint`, `-p`, `--init-model`, `--mdef`, `-te`, checkpoint and restart, export
  and `-m FILE`) against NQC's equivalent, classed as same, differs or refused, with the reason.

A fresh subagent does the first read, given the code and IQ-TREE's base classes but not this
brief's conclusions, so that its read is not anchored on ours. Items already visible, which are
not yet findings:

- `fixedeq::solveStationary` mirrors `computeStateFreqFromQMatrix` (its own comment says so); the
  chart's purity required a copy.
- NQC overrides `optimizeParameters` and the derivative (decisions 005, 009).
- `NQC+F{...}` names the target, while `NONREV+F{...}` pins π with Q unconstrained (constraint 9;
  maintainer question 2).
- `--nqc-domain` and the `.NQC.qmat` and `.NQC.info` exports are new (maintainer question 8).
- On the maintainer's `-S` question: the first release's scope runs `--model-joint` under `-S` and
  `-p`, as nQMaker does. Whether an `-S` directory input, rather than a partition file, has been
  tested was not checked.

### Testing a refactor without re-validation

Binary `~/iqtree3-binaries/25d78d6e/iqtree3` (built from `36a43711`) is the latest IQ-TREE build
gated (PLAN.md); S5's gate ran against it and SIM-2 runs it. Earlier gates ran earlier builds, each
compared with its predecessor under decision 021's previous-build row. A refactor that reproduces
that binary's outputs bitwise at `-T 1`
on commands reaching every NQC entry point inherits the evidence of S1 to S5, SIM-1 and SIM-2
without re-running them. That is equivalence on a probe set, not a proof, so the set must cover
every path the change touches.

**Tier A: pure moves** (folding the hooks, moving the chart, renaming, comments). Tools that already
exist:

1. **Control build.** Decision 021's previous-build row requires the same toolchain, and
   `toolchain_changes` downgrades the check to "report" when Debian's toolchain packages changed
   after the previous binary was built. It reads only the two newest dpkg logs, not rotated `.gz`
   ones, so its verdict weakens with time. So the unchanged head is built first and checked bitwise
   against `25d78d6e`. That separates toolchain drift from the refactor's effects and measures the
   run time, which is unmeasured.
2. **Legacy models.** `regress.py run` and `compare` against the three baselines (constraint 4).
3. **NQC equivalence.** `nqcchecks.py`'s `same_outputs` compares layer 4's report sections, the
   tree file, NQC's checkpoint keys and the export files against the previous binary. Today it runs
   on 4 commands (Level 1, Level 1 with `-z`, `-S` Level 1, `-q` Level 1). It would be extended
   to: Level 2 with `+G4`, `+I+G4` and `+R4`; `-p` Level 2; `--link-model`; restart and `--undo`;
   export and re-import; every refusal (message and exit code); `--nqc-domain`; `--init-model`.
   Thread counts are compared under decision 038's lines, because the non-reversible kernel is not
   bitwise reproducible across calls above one thread (maintainer question 12).
4. **Chart unit tests.** `unittests.py`, with the fixtures unchanged.
5. **Sanitizers.** One `sanitize.py` run at the end of CR, before code goes to the maintainers, not
   after each step.

Bitwise output is expected but unverified. On x86 the `model` target's SSE flags are `-msse3`, with
`-mfma` only in the kernels' FMA flags (top-level `CMakeLists.txt`, read 2026-11-20), so the model
code cannot be contracted into FMA instructions. Moving functions into one translation unit lets the
compiler inline across what was a file boundary, which without fast-math and FMA should not change
results. If a result differs, work stops for diagnosis before anything else.

**Tier B: changes that alter numbers or the user interface** (replacing the chart's stationary
solve with IQ-TREE's, renaming an option, changing an output file). These break the property that
the submitted code is the code SIM-2 ran. Agent's recommendation: defer them until after SIM-2 and
the maintainers' reply, and list them for the maintainers as proposals. Their preferences may differ
from ours, and this avoids doing the work twice.

### Running beside SIM-2

- **Puma.** Each job runs the frozen binaries (the unmodified `~/iqtree3-baseline/iqtree3` and the
  gate binary `25d78d6e`) and Python from the clone Peter pulled at `22ef0db7`.
  CR touches neither, provided the frozen binary directory is never overwritten and nothing is
  pulled into the Puma clone between rounds. A side branch makes the second condition automatic.
- **Laptop.** Commit 4 (`sim2.py analyze`, Python under `sim/`) shares no file with CR except the
  records, so it can proceed on `nq-constrained-pi`. The laptop is also needed when round 1's
  tarballs arrive (each shard projected at about 41 to 45 h from its start); CR's runs should not
  compete with that analysis.

### Side branch

Recommended, and taken by Peter (below). Its main gains:

- `nq-constrained-pi` stays the exact code SIM-2 ran;
- CR can be dropped cheaply if the equivalence fails or the maintainers want another layout;
- `git diff nq-constrained-pi...<branch>` shows the refactor alone.

The protection it gives Puma is modest, since Puma runs a frozen binary.

Conditions found:

- **Decision 001** said "All work happens on `nq-constrained-pi`" and needed amending.
- **One working copy** (`CLAUDE.md`). The drivers check that the tree is clean only at start, so a
  branch switch during a build or driver run changes files under it. Never switch then. Build each
  branch in its own WSL directory, so that each binary's source is unambiguous.
- **CI.** `fixedeq.yaml` triggers only on pushes to `nq-constrained-pi`, so the branch adds its own
  name to the trigger, and a last commit on the branch removes it before the fast-forward (a merge
  cannot remove it).
- **Pushing.** `.claude/settings.json` allows only `git push origin nq-constrained-pi`, so pushing
  the branch needs Peter's approval each time, or a settings change he makes.
- **Merging.** Merge `nq-constrained-pi` into the branch, resolve conflicts there (expected only in
  `CHANGELOG.md`'s top entries and PLAN.md's current state), re-run the equivalence, remove the
  trigger line, then fast-forward `nq-constrained-pi`. Never rebase or squash, because the records
  cite commit hashes. The merge waits for SIM-2's last round to be submitted unless Peter allows it
  earlier, so that no pull for a round brings CR's code into Puma's clone.
